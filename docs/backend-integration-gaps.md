# Заглушки и точки подключения после дополнения концепции

Фронтенд работает локально. `src/services.ts` — явная граница: методы возвращают `state: not_connected`, не выполняют HTTP-запросы и не подтверждают банковские операции. UI показывает, чего ещё нет. Готовое общее ТЗ API — BACKEND_CODEX_PROMPT.md.

| В интерфейсе | Сейчас | После подключения |
|---|---|---|
| Срок этапа и обновление статуса | refreshStatus, ETA=null; только время локальной попытки проверки | GET заявки, currentStage и estimatedNextStageAt из общего контракта; polling 5 с |
| Условия сопутствующего продукта | getProductTerms, тариф и решение отсутствуют | Подбор доступных банковских предложений для авторизованного клиента |
| Данные погашения | Дата, остаток и статус оплаты отсутствуют; отдельно есть математическая модель | Данные действующего кредита и история платежей |
| Обращение по погашению | sendSupportRequest возвращает requestId=null; сохраняется только локальный черновик | Серверное создание обращения с реальным ID и подтверждением приёма |

## Предлагаемое расширение API (проект, не реализован)

Сохраняются JWT, владение данными, форматы ошибок и единицы из основного контракта.

- `PUT /api/v1/product-fit`: `{ "goal": "turnover|equipment|growth", "channel": "online|offline|b2b", "priority": "payments|cashgap|reserve" }`. Сохранить ответы текущего клиента. `GET /product-fit` возвращает ответы или 404. Ответы не равны доступному кредитному предложению.
- `GET /api/v1/product-fit/recommendations`: категории с id/title/description/reason; персональные предложения — только после реальной проверки. Отсутствующий тариф = null. Никаких выдуманных ставок/доходности.
- `GET /api/v1/products/{id}/terms`: доступность, тарифы, ограничения и дата актуальности; пока интеграции нет — структурированное состояние not_connected, а не фиктивный тариф.
- `GET /api/v1/applications/{id}/repayment`: фактические nextPaymentAt, nextPaymentAmount, outstandingPrincipal, paymentStatus, payments[]. До реальной выдачи/подключения — null и явное состояние; frontend-модель не записывать как оплаченные платежи.
- `POST /api/v1/applications/{id}/support-requests`: `{ "topic": "...", "message": "..." }`, обязательная идемпотентность. 201 с requestId/status/createdAt только после реального сохранения. Если шлюз банка ещё не принял обращение, status должен различать локальный приём сервисом и отправку банку.
- `POST /api/v1/analytics/events` из основного контракта дополняется SURVEY_COMPLETED. Очередь события содержит eventId/name/createdAt/applicationId=null; перед доставкой фронт связывает события с настоящей заявкой, если это уместно. Время клиента — clientCreatedAt; сервер фиксирует собственное createdAt. Не отправлять деньги, имена, ИНН, заметки обращения и документы в аналитику.

## Локальные данные

`alfa-product-fit-v1`: answers {goal,channel,priority}, completed, step. `alfa-repayment-request-v1`: topic, note, savedAt. `alfa-analytics-v1`: до 200 событий без персональных полей; повторная доставка должна использовать исходный eventId. Очередь пока не отправляется автоматически.

Новым отправленным заявкам сохраняются submittedTerms {amount,rate,months,purpose}. Модель погашения использует их. Для старых демо-заявок без snapshot берутся сохранённая сумма и последние параметры калькулятора; это только модель. После API-интеграции все фактические условия должны приходить из неизменяемого snapshot заявки/договора.

## Что закрывается во фронте

Инструкции по документам и обязательности файла, исправление смены типа бизнеса, опрос, локальный подбор категорий, модель выплат и текст обращения. Медианное время обработки и долю заявок без повторных запросов нельзя достоверно вычислить по локальной очереди: для них нужны реальные события процесса на сервере.
