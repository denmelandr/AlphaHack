## 1. Продукт и границы

Кабинет малого бизнеса содержит пять разделов: Обзор, Калькулятор выгоды, Заявка, Статус заявки, Документы. Пользователь рассчитывает кредит, заполняет четыре шага анкеты, загружает документы, отправляет заявку и видит её путь до решения и демонстрационной выдачи.

Нужен один монолит, без микросервисов, Redis, Kafka, Celery, LLM, SMS и почтовых интеграций. Реального банка, ФНС, БКИ, электронного подписания и денежных переводов нет. Все банковские действия — явно обозначенная симуляция на синтетических данных. Не выдавай правило демо-одобрения за реальный скоринг.

Первый приоритет: сохранение черновика, документы, серверная валидация отправки и последовательные статусы. Второй: калькулятор и график, уведомления, демонстрационная обработка, метрики.

## 2. Стек и запуск

- Python 3.12, FastAPI, Pydantic 2, SQLAlchemy 2, Alembic, PostgreSQL 16, psycopg, Uvicorn.
- Синхронный SQLAlchemy и обычные `def`-эндпоинты допустимы и предпочтительны для быстроты реализации. Не вызывай блокирующие операции БД из `async def` напрямую.
- `python-multipart` для файлов, PyJWT и pwdlib с Argon2 для входа, pytest и httpx для тестов.
- Выбери совместимые доступные версии, зафиксируй зависимости lock-файлом. Не записывай выдуманные номера версий.
- Файлы — каталог `/app/storage` в отдельном именованном Docker volume; метаданные — PostgreSQL. Интерфейс файлового хранилища выдели в сервис, чтобы позднее заменить на S3.
- `docker compose up --build`: БД, миграции и идемпотентный seed, затем API на `http://localhost:8000`. Нужны healthcheck и ожидание готовности БД. Данные переживают обычный restart.
- Переменные: `DATABASE_URL`, `JWT_SECRET`, `ACCESS_TOKEN_EXPIRE_MINUTES=60`, `CORS_ORIGINS`, `STORAGE_PATH`, `MAX_UPLOAD_BYTES=10485760`, `DEMO_MODE=false`. В `.env.example` — примеры. Секрет не коммитить.
- Для локальной демонстрации README объясняет `DEMO_MODE=true`. Сидирование демо-аккаунтов и demo-роуты работают только в этом режиме.
- CORS: явные origins `http://localhost:5173`, `http://127.0.0.1:5173`; методы GET, POST, PATCH, DELETE, OPTIONS; заголовки Authorization, Content-Type, Idempotency-Key. Не ставь `*` вместе с credentials. Cookie-auth в этом MVP не используется.
- Swagger `/docs`, спецификация `/openapi.json`, также сохрани сгенерированную спецификацию в `docs/openapi.json`.

## 3. Общие правила контракта

Базовый путь `/api/v1`. JSON в UTF-8. Имена полей в camelCase либо в текущем написании фронта, как в примерах ниже: не преобразовывай их в snake_case в ответах. Pydantic aliases допустимы.

- ID сущностей: UUID в строках; `number` заявки — отдельный читаемый номер, генерируется сервером и уникален.
- Все даты: ISO 8601 UTC с `Z`; отображение локального времени делает фронт.
- Валюта RUB. Суммы в рублях, JSON number, максимум 2 знака после запятой. В Python и PostgreSQL — Decimal / NUMERIC, а не float; явно сериализуй денежные Decimal как JSON number согласно контракту. Никаких NaN/Infinity.
- Ставка — проценты годовых: `24` означает 24%, а не 0.24.
- Неизвестные входные поля отклонять. Серверные поля нельзя менять через PATCH.
- У каждой заявки `revision`, начиная с 1. Любое изменение данных, документов, запросов документов и статуса увеличивает revision. Пересчёт readiness при GET её не изменяет.
- GET чужой заявки/документа/уведомления возвращает 404, чтобы не раскрывать существование чужих объектов. JWT без прав на банковские demo-операции — 403.
- Списки: `{ "items": [...], "total": 12 }`, параметры `limit` (1–100, по умолчанию 20), `offset` (>=0). Порядок заявок и уведомлений — новые сначала. Если явно не указан иной порядок, используй createdAt DESC, id DESC.

Единая ошибка, включая ошибки Pydantic:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Проверьте данные заявки",
    "fields": {
      "inn": "ИНН должен содержать 10 или 12 цифр",
      "email": "Некорректный адрес"
    },
    "requestId": "9d4790de-ae33-4012-b9c6-14e399d72c75"
  }
}
```

Коды: 400 INVALID_REQUEST; 401 UNAUTHORIZED; 403 FORBIDDEN; 404 NOT_FOUND; 409 REVISION_CONFLICT / INVALID_TRANSITION / APPLICATION_LOCKED / IDEMPOTENCY_CONFLICT / DOCUMENT_REQUEST_PENDING; 413 FILE_TOO_LARGE; 415 UNSUPPORTED_FILE_TYPE; 422 VALIDATION_ERROR; 503 STORAGE_UNAVAILABLE. Для ошибок без привязки к полям `fields: {}`. Внутренние детали исключений и пути хранения клиенту не показывать. Возвращать `X-Request-ID` и логировать этот идентификатор.

## 4. Вход и владелец данных

Минимальная JWT-авторизация, два demo-аккаунта: `client@demo.local` и `bank@demo.local`. Пароли заданы только как синтетические значения в demo-конфигурации/seed и описаны в README; хранятся в БД как хэши. Не подключай реальные учётные записи.

`POST /auth/login` — JSON:

```json
{ "email": "client@demo.local", "password": "demo-client-password" }
```

200:

```json
{ "accessToken": "<jwt>", "tokenType": "bearer", "expiresIn": 3600 }
```

На защищённых маршрутах `Authorization: Bearer <jwt>`. Используй HTTPBearer, поскольку вход принимает JSON, а не OAuth form. Проверяй подпись, разрешённый алгоритм, срок действия и существование пользователя. Роль брать из проверенного пользователя, не из входного JSON. Ошибки входа — общее сообщение без раскрытия существования email.

`GET /me` → `{ "id": "<uuid>", "name": "Тестовый Предприниматель", "email": "client@demo.local", "role": "client" }`.

Refresh и регистрация не нужны. При истечении токена — 401, фронт снова показывает вход. Кроме `/auth/login`, `/health/live`, `/health/ready`, остальные маршруты API требуют JWT. `client` работает со своими заявками; `bank` — только с demo-обработкой и агрегированными demo-метриками.

## 5. Данные заявки и совместимость с фронтом

Сохраняй плоские имена полей из текущего `Draft`:

| Поле | Тип и смысл |
|---|---|
| amount | number, 100000–10000000 ₽ |
| rate | number, 0–60 % годовых |
| months | integer, одно из 6, 12, 18, 24, 36, 48, 60 |
| profit | number, 0–10000000 ₽, доп. прибыль в месяц после расходов и налогов, до платежа по кредиту |
| delay | integer, одно из 0, 1, 2, 3, 6; меньше months |
| purpose | строка из перечисления ниже |
| company | строка, до 200 символов |
| inn | строка, сохранять ведущие нули |
| type | `ИП` или `ООО` |
| name | контактное лицо, строка до 150 символов |
| email | контактная почта заявки, не логин аккаунта |
| revenue | number или null; среднемесячная выручка |
| expenses | number или null; среднемесячные расходы |
| step | integer 0–3: бизнес, финансы, документы, проверка |
| consent | boolean, согласие на demo-обработку |

`purpose`: `Реклама и продвижение`, `Закупка товара`, `Оборудование`, `Развитие бизнеса`, `Пополнение оборотных средств`.

Фронт сейчас хранит revenue/expenses строками, пустую строку при отправке надо переводить в null, заполненную — в number. Бэкенд возвращает number|null.

Частичный черновик допустим: company, inn, name, email могут быть пустыми; revenue/expenses — null. Непустые значения проверять по формату при PATCH. ИНН — 10 или 12 цифр, без контрольной суммы, чтобы синтетический `000000000000` работал. Длину по форме ИП/ООО дополнительно не ограничивать: это намеренное упрощение под текущий фронт.

Не принимать `status`, `statusCode`, `decision`, `number`, `ownerId`, `submitted`, `submittedAmount`, `docs`, `readiness`, `notifications`, `revision` как редактируемые поля заявки.

## 6. Эндпоинты черновика

### POST /applications

Тело — необязательные редактируемые поля из таблицы; пустой объект создаёт черновик с текущими дефолтами: amount=1000000, rate=24, months=24, profit=95000, delay=0, purpose=Реклама и продвижение, type=ИП, step=0, consent=false; строки пустые; финансы null.

201 → полный ApplicationResponse. Владелец — текущий client. В MVP поддерживай одну незавершённую заявку на владельца: если уже есть черновик или заявка в процессе рассмотрения, верни её с 200, не создавай дубль. Защити от гонки транзакцией/ограничением БД. После DISBURSED или DECISION с REJECTED разрешается создать новый черновик.

### GET /applications

Список своих полных ApplicationResponse с limit/offset. Для восстановления текущего кабинета фронт запрашивает `GET /applications/current`: приоритет единственной активной заявки, иначе последняя завершённая, иначе 404. Это отдельный маршрут, объяви его до `/{id}`.

### GET /applications/{id}

200 → полный ApplicationResponse.

### PATCH /applications/{id}

Частичный JSON из редактируемых полей + обязательный `expectedRevision`:

```json
{ "expectedRevision": 4, "company": "ИП Тестовый бизнес", "revenue": 1500000, "expenses": 900000, "step": 1 }
```

200 → полный ApplicationResponse с новой revision. Неуказанные поля сохраняются. null допустим только для revenue/expenses. Проверку expectedRevision и изменение делать атомарно; устаревшая версия → 409 REVISION_CONFLICT. Черновик должен сохраняться без требования заполнить все шаги. Сам `step` не означает готовность.

PATCH разрешён только в DRAFT, иначе 409 APPLICATION_LOCKED. При смене type уже загруженный `report` становится неактуальным: отвяжи/удали его и потребуй загрузить заново; passport и statement остаются. Обновление и инвалидирование документа — одна логическая транзакция.

### POST /applications/{id}/validate

Тело `{}`. 200 → объект readiness точно в формате выше; проверяет сохранённые сервером данные, не доверяет readiness от клиента. Не меняет статус, шаг и revision.

Четыре равновесные проверки дают 0/25/50/75/100%:

1. company: непустые company/name, ИНН 10/12 цифр, корректный email.
2. finance: revenue > 0; expenses >= 0; оба заполнены; expenses < revenue.
3. documents: все три актуальных обязательных документа загружены.
4. consent: true.

canSubmit = все четыре проверки true И statusCode=DRAFT. После отправки readiness отражает комплектность, но canSubmit=false, повторную отправку обрабатывает идемпотентный submit. Добавь ошибки `docs`, `consent`, `company`, `inn`, `name`, `email`, `revenue`, `expenses` по необходимости. Если текущего потока не хватает на платёж, это предупреждение; само по себе оно не блокирует submit.

### POST /applications/{id}/submit

Тело `{ "expectedRevision": 7 }`. Обязательный заголовок `Idempotency-Key: <uuid>`.

Сервер атомарно проверяет revision и validate, фиксирует согласие и его время, submitted/submittedAmount, переводит DRAFT→SUBMITTED, создаёт историю и уведомление. 200 → полный ApplicationResponse.

Неготовая анкета → 422 с errors readiness в error.fields, статус остаётся DRAFT. Проверку повторного Idempotency-Key выполняй ДО проверки revision: тот же пользователь + маршрут + ключ + идентичное тело возвращают сохранённый первый успешный ответ даже при старой revision. Другой payload на том же ключе → 409 IDEMPOTENCY_CONFLICT. Новый ключ для уже отправленной заявки → 409 INVALID_TRANSITION. Два одновременных вызова не создают два перехода/два уведомления.

## 7. Документы и запросы банка

Основные ключи `passport`, `statement`, `report`. Дополнительный ключ `extra` зарезервирован для единственного demo-запроса выписки. `report` для ИП называется «Налоговая декларация», для ООО — «Бухгалтерская отчётность».

### POST /applications/{id}/documents

`multipart/form-data`:

- `file`: бинарный файл;
- `kind`: passport | statement | report | extra;
- `expectedRevision`: integer;
- `requestId`: UUID, обязателен для extra, для основных документов отсутствует.

Используй UploadFile + Form; не требуй одновременно JSON body. Лимит 10 МиБ, PDF/JPEG/PNG. Проверяй объявленный MIME, расширение и сигнатуру содержимого; потоковое чтение с ограничением размера, 413 при превышении. Пустой файл → 422. Храни под случайным серверным именем, исключи path traversal. Исходное имя сохраняется только как безопасные метаданные. Файлы не публикуются через StaticFiles. При сбое/гонке очищай временные файлы, не оставляй строки с несуществующим файлом.

Основные документы загружаются и заменяются только в DRAFT; один активный файл на kind. `extra` принимается только по открытому запросу своей заявки в DOCUMENT_REVIEW. Принятый extra связывается с requestId и переводит запрос в FULFILLED. Замена основного документа атомарна: при неудаче старый остаётся доступен. revision увеличивается.

201:

```json
{
  "revision": 8,
  "document": {
    "id": "297c1d8f-1b75-4e08-bd54-ab2799589f00",
    "kind": "passport",
    "name": "passport-demo.pdf",
    "size": 14502,
    "contentType": "application/pdf",
    "uploadedAt": "2026-10-22T12:10:00Z",
    "requestId": null,
    "downloadUrl": "/api/v1/applications/53f951e9-1d66-4ec3-85ec-847b873e2ddc/documents/297c1d8f-1b75-4e08-bd54-ab2799589f00/download"
  }
}
```

`ApplicationResponse.docs` — словарь kind → такой же объект document. Data URL и содержимое файлов в JSON больше НЕ возвращать. После загрузки фронт делает GET заявки, чтобы обновить readiness и запросы.

### GET /applications/{id}/documents/{documentId}/download

Возвращает бинарное содержимое с корректными Content-Type и Content-Disposition attachment. Проверяй владельца и принадлежность документа заявке. Фронт скачивает через fetch с Bearer, затем Blob/object URL; обычный `<a>` не добавляет Authorization. URL не содержит токенов.

### DELETE /applications/{id}/documents/{documentId}?expectedRevision=8

Только свой основной документ в DRAFT. 200 → `{ "revision": 9 }`; readiness станет неготовым. После отправки удаление запрещено 409 APPLICATION_LOCKED. Дополнительный документ выполненного запроса не удаляется через этот маршрут.

### Модель DocumentRequest

```json
{
  "id": "0ac7237a-d582-4dbd-82eb-e4e2ce19bbdb",
  "kind": "extra",
  "title": "Выписка за последний месяц",
  "reason": "Нужна для уточнения актуального денежного потока",
  "instructions": "Загрузите выписку по расчётному счёту в PDF, JPG или PNG",
  "status": "OPEN",
  "documentId": null,
  "createdAt": "2026-10-22T12:15:00Z",
  "fulfilledAt": null
}
```

Статусы запроса OPEN/FULFILLED. Он не меняет основной статус заявки на отдельное число. Запрос и его выполнение создают события и уведомления.

## 8. Статусы и банковский симулятор

Число `status` сохраняет совместимость с текущим интерфейсом:

| statusCode | status | Подпись |
|---|---:|---|
| DRAFT | -1 | Черновик |
| SUBMITTED | 0 | Заявка отправлена |
| DOCUMENT_REVIEW | 1 | Проверка документов |
| BANK_REVIEW | 2 | Оценка банком |
| DECISION | 3 | Решение |
| DISBURSED | 4 | Выдача |

`decision`: null до решения; далее `{ "outcome": "APPROVED" | "REJECTED", "reason": "...", "decidedAt": "..." }`. DECISION + REJECTED — конечное состояние, выдача запрещена. DECISION + APPROVED допускает DISBURSED.

Переходы последовательные. При первом SUBMITTED→DOCUMENT_REVIEW demo-сервис создаёт ОДИН OPEN-запрос extra. До его выполнения переход в BANK_REVIEW возвращает 409 DOCUMENT_REQUEST_PENDING. Повторные нажатия не создают дубли запросов.

### POST /demo/applications/{id}/advance

Только роль bank и DEMO_MODE=true; в обычном режиме маршрут не регистрируется (404). JSON `{ "expectedRevision": 10 }`, обязательный Idempotency-Key с теми же правилами повторов, что у submit. Bank может обработать demo-заявку любого demo-client, читать файлы через этот endpoint не может.

Продвигает ровно на один допустимый этап, 200 → полный ApplicationResponse. При BANK_REVIEW→DECISION демо-правило: `revenue - expenses >= monthlyPayment` → APPROVED; иначе REJECTED с понятным текстом. Используй сохранённые условия заявки. Это воспроизводимое учебное правило, не реальный скоринг. Ни риск, ни результат не принимаются от клиента.

При переходе в DISBURSED ничего не переводится, текст явно «Демонстрационная выдача завершена». Каждый переход и создание связанного запроса/уведомления — транзакция. Между этапами не должно быть cron/timer или процесса только в памяти. После рестарта всё восстанавливается из БД.

`currentStage` вычисляется сервером. Если есть OPEN-запрос — nextAction объясняет загрузку конкретного документа. Если действий нет — nextAction=null. Реальные ETA неизвестны: estimatedNextStageAt=null и честное etaDescription; не генерировать выдуманный SLA. Для завершённых заявок сроки не обещать.

### GET /applications/{id}/events

JSON-история событий: `{ "items": [...], "total": N }`, с limit/offset; порядок createdAt ASC, id ASC. Каждое событие: id, type, fromStatusCode (nullable), toStatusCode (nullable), message, createdAt, actorRole. Типы: APPLICATION_SUBMITTED, STATUS_CHANGED, DOCUMENT_REQUESTED, DOCUMENT_PROVIDED, DECISION_MADE, DEMO_DISBURSED. Серверные данные, клиент их не создаёт.

ВАЖНО: в этом MVP events — обычный JSON endpoint, не SSE. Более ранняя схема в общей архитектуре фронта упоминала SSE; этот контракт v1 заменяет её. Фронт опрашивает GET заявки раз в 5 секунд на экране трекера, приостанавливает опрос в скрытой вкладке и после конечного состояния. Не вводи WebSocket/SSE в первую реализацию.

## 9. Уведомления

`GET /notifications?limit=20&offset=0&unreadOnly=false` → `{ "items": [...], "total": 5, "unreadCount": 2 }`. total учитывает фильтр, unreadCount — все непрочитанные уведомления текущего пользователя.

Объект: id, applicationId, type (как у событий), title, message, createdAt, readAt (null или дата). Не показывать чужие уведомления. Строки вроде «расчёт перенесён» или «файл сохранён» могут остаться локальными toast; сервер хранит события процесса.

`PATCH /notifications/{id}` с `{ "read": true }` → обновлённый объект, повтор безопасен, readAt не изменяется при повторном чтении. Возврат в непрочитанные для MVP не нужен.

## 10. Калькулятор и график

`POST /calculations` принимает:

```json
{ "amount": 1000000, "rate": 24, "months": 24, "profit": 95000, "delay": 0, "scenario": "base" }
```

scenario: low/base/high; коэффициенты 0.7/1/1.2. Ограничения полей как у заявки. amount > 0 гарантирован, months > 0, потому деление на ноль недопустимо. Расчёт не создаёт заявку.

Формулы соответствуют текущему `src/finance.ts`:

- r = rate / 1200;
- payment = amount / months при r=0; иначе amount × r / (1 - (1+r)^(-months));
- interest = payment × months - amount;
- total = amount + interest;
- effectiveProfit = profit × scenarioFactor;
- projectedProfit = effectiveProfit × max(0, months-delay);
- benefit = projectedProfit-interest;
- coverage = effectiveProfit/payment;
- shortage = effectiveProfit < payment ИЛИ delay > 0;
- reserveRequired = payment × delay.

200:

```json
{
  "payment": 52871.10,
  "interest": 268906.33,
  "total": 1268906.33,
  "projectedProfit": 2280000,
  "benefit": 2011093.67,
  "coverage": 1.7968,
  "shortage": false,
  "reserveRequired": 0,
  "effectiveProfit": 95000,
  "scenario": "base",
  "warnings": [],
  "isPreliminary": true
}
```

Считай с высокой внутренней точностью, деньги округляй HALF_UP до копеек на выдаче; coverage до 4 знаков. Возможное расхождение с JS-фронтом до нескольких копеек допускается, сервер — источник итоговых значений. `warnings`: массив `{ "code": "CASHFLOW_SHORTAGE" | "DELAY_RESERVE_REQUIRED" | "NEGATIVE_BENEFIT", "message": "..." }` по применимым условиям.

Выгода — прибыль минус проценты, а не гарантия окупаемости вложений; возврат основного долга учитывается отдельным предупреждением о денежном потоке. Никаких актуальных рыночных ставок или банковских обещаний.

`POST /calculations/schedule` принимает те же поля и возвращает `{ "items": [{ "month": 1, "payment": 52871.10, "interest": 20000, "principal": 32871.10, "balance": 967128.90 }], "totalPayment": ..., "totalInterest": ... }`. Все месяцы 1..months. Платёж в графике округляется до копеек, финальный корректируется до закрытия долга. Сумма principal равна amount, конечный balance=0.00. Суммы графика могут отличаться на копейки от формулы без промежуточного округления — отразить это в README.

`POST /calculations/schedule.csv` с тем же JSON → UTF-8 BOM CSV, разделитель `;`, поля `Месяц;Платёж;Проценты;Основной долг;Остаток`. Бери те же строки, что в JSON schedule.

## 11. Таблицы и транзакции

Минимум: users; applications; documents; document_requests; application_events; notifications; idempotency_records. В applications — все поля анкеты, statusCode, decision, revision, временные метки, snapshot при отправке. Владелец связан по FK. Для простого MVP отдельная таблица компаний не требуется: меню бизнеса берёт реквизиты текущей заявки.

Обязательно уникальный читаемый number, один активный документ на (application_id, kind), один extra-запрос для demo-заявки, уникальность идемпотентности (actor_id, method, path, key). Активная заявка на пользователя тоже защищена от гонки. Revision сверять и менять внутри транзакции/row lock. Загрузка или удаление файла, ошибка транзакции и очистка временного файла должны быть согласованы.

Не логировать JWT, пароли, содержимое документов. Ошибки файлового хранилища не должны портить заявку. Область MVP — локальное demo на синтетических данных, не production-хранение паспортов.

## 12. Минимальная аналитика

Источники событий: создания/отправки/валидации заявок, документы, смена статуса, решения. Для пользовательской воронки добавь `POST /analytics/events`, 202 `{ "accepted": true }`:

```json
{ "eventId": "<uuid>", "name": "BENEFIT_EVALUATION_COMPLETED", "applicationId": null }
```

Разрешённые names: CALCULATOR_OPENED, BENEFIT_EVALUATION_COMPLETED, SUBMIT_ATTEMPTED, STATUS_HELP_OPENED, SURVEY_COMPLETED. Дедупликация по (user_id,eventId), время сервера, владелец applicationId проверяется. Не принимать произвольные персональные данные/свободные properties. События этапов обработки не разрешать создавать этим маршрутом.

`GET /demo/metrics` — bank + DEMO_MODE=true: количество уникальных клиентов с CALCULATOR_OPENED и с BENEFIT_EVALUATION_COMPLETED; конверсия = завершившие среди открывших / открывшие, null при нулевом знаменателе. Дополнительно submittedCount, applicationsWithoutDocumentRequestsCount и их доля; medianDecisionSeconds от submitted до decision; statusHelpOpenCount. Отсутствующие данные — null/0 по смыслу, не выдумывать проценты. Опрос справки — proxy, не реальное обращение в поддержку; запросы документов — proxy, не доказательство ошибок клиента. Укажи эти определения в ответе/README.

## 13. Что потребуется фронтенду при подключении

Это инструкции интеграции, не требование переписать фронт прямо сейчас:

1. `VITE_API_BASE_URL=http://localhost:8000/api/v1`, общий fetch-клиент и JWT в памяти. Не вшивать демо-пароли или bank-token в клиентскую сборку. На первое подключение нужен небольшой экран входа с demo-client.
2. Загрузить `/me`, `/applications/current`; если 404 — создать черновик. После reload восстанавливать данные с сервера, локальный applicationId — только указатель, не источник истины.
3. Автосохранение PATCH с debounce 500–800 мс, ожидаемая revision из последнего ответа. Сериализовать мутации заявки, отменять ожидающий debounce при отправке, не отправлять параллельно с загрузкой документа. На 409 перечитать данные и предложить повтор; не затирать локально набранный текст молча.
4. «Прогресс сохранён» показывать только после успешного ответа. При ошибке — «Не удалось сохранить» с повтором. Перед submit дождаться всех сохранений/загрузок.
5. Заменить Data URL на метаданные документов и бинарные multipart-загрузки. Поднять UI-лимит с 800 КБ до 10 МиБ. При скачивании использовать авторизованный fetch.
6. Брать requiredDocuments/readiness/status/currentStage/documentRequests из API. Общие тексты интерфейса остаются во фронте. errors.fields маппить к текущим полям формы.
7. Объекты уведомлений маппить по id, а не по индексу; отображать message, читать через PATCH.
8. На трекере polling 5 секунд. Новые статусы/уведомления определять по id/revision, не генерировать повторные toast на каждый GET.
9. Дополнительную выписку загружать с requestId из OPEN-запроса. Наличие docs.extra само по себе не источник состояния банка.
10. При REJECTED показать причину и запретить выдачу. Существующий фронт пока показывает только положительный demo-путь — этот экран надо расширить.
11. Обычный client не вызывает demo/advance. Для показа обработки — Swagger с bank-логином или отдельная bank-панель; банковский токен в обычный кабинет не передавать.
12. Меню профиля/ИП можно оставить на данных текущей заявки; отображаемая личность входа — `/me`, контактное лицо заявки может отличаться.
13. Отправлять четыре пользовательских analytics-события по смыслу: открытие калькулятора; явный переход от оценки к заявке; попытка submit; открытие помощи именно со статуса. eventId генерировать один раз на логическое действие и переиспользовать при повторной сетевой отправке.

## 14. Приёмка и необходимые файлы

Подготовь:

- `app/main.py`, config, db, models, schemas, routers, services (расчёт, документы, статусы), обработчики ошибок; разумная структура без лишних абстракций.
- Alembic migrations, seed, Dockerfile, compose.yaml, .env.example, lock-файл.
- README: запуск, demo-логины, все допущения, схема состояний, модель БД, правила расчёта, curl-сценарий.
- `docs/openapi.json`, экспортированный из реального приложения, а не написанный вручную заглушкой.
- `scripts/smoke.sh` или эквивалент: login → create → patch → upload×3 → validate → submit → bank advance → upload extra клиентом → bank advance×3 → DISBURSED. Динамические id/revision брать из ответов, не хардкодить. Скрипт не должен требовать реальные документы.
- Синтетический валидный PDF/PNG, без персональных данных; не загружать скриншоты пользователя в тесты.
- Интеграционные pytest-тесты на реальном PostgreSQL в тестовом Compose/отдельной тестовой БД; не подтверждать PostgreSQL-ограничения исключительно SQLite-тестами.

Тесты должны проверять: пустой черновик сохраняется; неготовую заявку отправить нельзя; корректную можно; данные/документы переживают restart; чужие объекты недоступны; просроченный JWT отклоняется; client не может менять статус; обычный PATCH после submit запрещён; stale revision даёт 409; повтор submit с тем же ключом не дублирует событие; неверный/слишком большой файл отклоняется; документ ООО отличается от ИП и report инвалидируется при смене type; OPEN-запрос блокирует переход; extra закрывает запрос; approved может перейти в выдачу, rejected — нет; demo-роуты отсутствуют при DEMO_MODE=false; нулевая ставка, задержка и низкий денежный поток считаются корректно; график сходится к нулю; OpenAPI содержит реальные схемы и ошибки.

В конце работы дай: что реализовано, как запустить, ссылки на Swagger и спецификацию, выполненные проверки и известные ограничения. Не утверждай, что React уже подключён, если его fetch-адаптер не реализован.
