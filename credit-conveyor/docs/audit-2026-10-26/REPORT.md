## Критические дефекты, воспроизведённые в runtime

### A1. Кнопки применения действий сопровождения возвращают HTTP 500

`POST /applications/2/servicing/apply {"action":"restructure_extend"}` → 500.
Повторный GET показывает прежние срок и платёж.

Причина: `backend/app/services/servicing.py:148`. `apply_action` меняет ORM-объект, но для известных кодов не возвращает acc и не сохраняет журнал. Код сохранения оказался ниже `return` в другой функции, на строках 217–223. Обработчик API пытается сериализовать None. `ServicingRadar.tsx:76` не ловит ошибку для отображения в интерфейсе.

Исправить: вернуть сохранение, журнал и return внутрь apply_action; сохранять денежные события и факт исполнения; ловить и отображать ошибки UI; добавить API-тесты каждого действия.

### A2. Автопилот сообщает об успехе без устранения причины разрыва

После трёх API-запусков журнал содержит три collect_receivables, но каждый ответ возвращает тот же разрыв 113 316 ₽ и servicing_log=[]. Дополнительный запуск из интерфейса добавил четвёртую идентичную запись. Дебиторская задолженность и ликвидность не меняются: collect_receivables/factor_receivables в apply_action содержат pass.

Сохранённый журнал сам по себе не доказывает выполнение действия. Нужен отдельный жизненный цикл действия: запрошено/исполнено/отклонено, учёт поступившей суммы, изменение дебиторки и защита от повтора.

### A3. Выбранный стресс-тест не соответствует исполняемому сценарию

При падении выручки на 45% экран рекомендует мост на 356 514 ₽. Нажатие «Прогнать сейчас» добавляет collect_receivables по базовому разрыву 113 316 ₽. Frontend отправляет стресс только в forecast; run_autopilot и apply принимают лишь ID/код действия и повторно строят базовый прогноз.

Для what-if нужно явно отключать реальное применение либо передавать версию/идентификатор исполняемого сценария и повторно валидировать его на сервере.

### A4. Мост предлагается даже без предодобрения; предодобрение не проверяется исполнителем

При -45% ответ содержит recommended=bridge и bridge.preapproved=false; UI всё равно называет действие «Предодобренный мост» и показывает кнопку применения. В run_autopilot проверяется max_bridge, но не preapproved. Отдельная проверка функции с заданным radar(preapproved=false) подтвердила выполнение bridge. Повторные вызовы не имеют ключа идемпотентности и могут повторять начисление долга.

Кроме того, кандидатный прогноз просто добавляет мост к ликвидности без пересчёта увеличенного платежа, а apply_action добавляет его к долгу и меняет платёж. Поэтому показанный результат не соответствует результату исполнения даже после устранения A1.

### A5. Ручное одобрение создаёт OFFER без оффера и оставляет старый отказ

В чистом seed Клён — заявка №4, DECLINED, без offer.
`POST /applications/4/review` → MANUAL_REVIEW;
`POST /applications/4/transition {"event":"manual_approve"}` → OFFER, offer=null, decision.outcome=decline;
`POST /applications/4/accept` → 409 «По заявке нет оффера».

Переход статуса не создаёт ни нового Decision, ни Offer. Нужна атомарная операция ручного решения с обоснованием и актуальными условиями.

### A6. Банковская роль может обойти принятие условий клиентом

Вошёл как underwriter@bank.ru. Для Ромашки вызовы transition: accept_offer → start_signing → disburse все вернули 200. Заявка перешла в SERVICING, хотя offer.accepted остался false. Общий transition проверяет только is_bank и допустимость события по состоянию, без разграничения событий по роли и бизнес-предусловий.

Это отличается от специального /accept, который отмечает offer.accepted. Нужно запретить клиентские/внутренние события через банковский endpoint и проверять принятый актуальный оффер перед выдачей.

## Ошибки расчётов и валидации

### B1. Нет строгой схемы YAML-политики

`POST /policies/simulate {"yaml_text":"score_bands: []","limit":50}` → 500.
_parse_yaml проверяет только dict и наличие score_bands. Объект с такой структурой допускается до сохранения/активации. Нужны типы, диапазоны, согласованность counter_min <= approve_min, допустимые поля/операторы ковенант и стоп-факторов. Сохранение и активация должны повторять валидацию; некорректная политика не должна выводить весь pipeline из строя.

### B2. API принимает отрицательные суммы и сроки, падение выручки более 100%

simulate(-100000, -2) → HTTP 200, контрпредложение -60 000 ₽.
forecast(revenue_drop_pct=200, extra_expense=-1000000) → HTTP 200.
AutopilotConfig(max_bridge=-100000) также проходит Pydantic.
Ограничения ползунков не защищают API. Нужны finite numbers, пределы суммы/срока продукта и независимая серверная проверка.

### B3. Уменьшенная сумма оффера может оказаться ниже минимума продукта

Прямая проверка policy.decide: min_amount=100000, подтверждённая месячная выручка 100, запрошено 1 млн на 12 месяцев, score=90 → оффер 427,38 ₽. После affordability-корректировки минимум продукта не проверяется.

### B4. «Цена бездействия» подменяет любой дефицит пропуском кредитного платежа

forecast.radar формирует missed_payment из текущего кредитного платежа при любом отрицательном остатке. Модель учитывает также зарплату, налог и разовый расход; первая дата дефицита может не быть датой платежа банку. Пени считаются как payment * 0.001 * 30. Это допущение, а не доказательство пропуска платежа или фактически начисленных пеней. Нужно показывать конкретное обязательство, которое не покрыто, и отдельно раскрыть допущения.

### B5. Расчёт стоимости моста не совпадает со способом его погашения

_action_cost считает приблизительно один месяц процентов по gap. Исполнение же добавляет gap к основной задолженности и амортизирует весь баланс на оставшийся срок. Показанная стоимость может существенно занижать фактическую стоимость смоделированного действия.

### B6. Метрики портфеля не связаны с успешным исполнением

Вычисление preventive_share и projected_30dpd_reduction использует bool(acc.servicing_log), тогда как автопилот пишет в acc.autopilot.log. Поэтому фактически проведённые вызовы не учитываются.
Даже после исправления журнала одного факта любого действия недостаточно для вывода о предотвращённой просрочке. Числа 8% и 35% — фиксированные допущения. Доход от кросс-продаж считается как число кредитов * 0.3 * 4000 и не зависит от числа предложений/покупок; так и следует подписывать в продукте.

- В общей очереди и карточке отсутствуют имя компании/ИНН. Нельзя надёжно выбрать «Ромашку» или «Весну» по названию без памяти о номерах. Исторические статусы в очереди показаны кодами OFFER/SERVICING/DECLINED.
- В account Весны 24 месяца и платёж 51 878,15 ₽, а в исходном offer/шапке 18 месяцев и 65 728,65 ₽. Это допустимо как история реструктуризации, но журнал этого действия пуст. На показе разница выглядит необъяснимой.
- Кнопки сохранения версии/активации политики скрыты от demo из-за `isRisk = user.role === "risk_admin"`; при этом backend разрешает demo. Для показа сохранения нужно входить risk@bank.ru / bank123 либо согласовать условия UI с сервером.
- Изменение только approve_min 70 → 60 не меняет исходы исходного портфеля; для наглядной симуляции можно изменить counter_min 45 → 35: Клён переходит decline → counter.
- Данные прогноза и проверки должников берутся из сохранённого enrichment, автоматического обновления внешних источников нет. Нельзя называть это непрерывным мониторингом уже подключённых источников.
- Документы в новой версии — метаданные. Кнопка «Загрузить» не передаёт реальный PDF; это раскрыто в README, но должно быть ясно и на экране.
- Черновик не восстанавливается в мастере: appId/шаг только в React state, нет загрузки существующей заявки по ID. Из NEEDS_INFO нет полноценного UI редактирования/дозагрузки; кнопка переотправки без исправлений возвращает на тот же этап.
- Смена продукта в мастере после создания черновика не обновляет product_id в серверной заявке; расчёт и перечень документов могут относиться к разным продуктам.
- При настройке лимита автопилота 0 после повторного входа UI использует `ap.max_bridge || 100000` и показывает 100 тыс. вместо сохранённого нуля. Нужен ?? и синхронизация state с обновлённым account.
- Ошибки запросов радара игнорируются, в apply/save/run нет catch с сообщением пользователю. «Применить» может выглядеть как неработающая кнопка.
- Shadow сравнивает только outcome на сохранённых score/profile. Изменение ставки/условий при неизменном outcome в diffs не видно. Это не оценка качества scorecard, дефолтов или эффекта ковенант сопровождения.
