# Security и production hardening

Документ фиксирует, что уже есть в прототипе и что потребуется усилить перед промышленной
эксплуатацией. Демо не подключается к реальным банковским системам и использует только
синтетические данные.

## Реализовано в MVP

- JWT-аутентификация;
- RBAC для клиентских, банковских и demo-ролей;
- проверка принадлежности заявки компании;
- отдельные права на клиентские и банковские операции;
- аудит переходов state machine;
- аудит policy-версий и их активации;
- секреты вынесены в `.env`, в репозитории только `.env.example`;
- внешние источники заменены локальными моками;
- LLM выключена по умолчанию и не нужна для основного сценария;
- документы в демо представлены только синтетическими метаданными;
- миграции схемы выполняются Alembic при старте backend.

## Ограничения демонстрационной конфигурации

- `JWT_SECRET` имеет dev-значение в `.env.example`;
- пароли демо-пользователей известны и находятся в seed-коде;
- CORS разрешает локальный frontend;
- Docker-порты PostgreSQL и Redis опубликованы на localhost;
- rate limiting, mTLS, WAF и централизованная ротация секретов не включены;
- интеграции не подписывают запросы и не используют реальные сертификаты.

Эти настройки приемлемы только для локального хакатонного запуска.

## Что изменить перед production

1. Использовать secrets manager, короткоживущие JWT и ротацию ключей.
2. Перенести identity и MFA в корпоративный IdP.
3. Убрать seed-пароли и demo-роль из production-сборки.
4. Не публиковать PostgreSQL/Redis наружу; закрыть сервисную сеть.
5. Добавить rate limiting, request size limits и защиту от повторной отправки команд.
6. Ввести idempotency keys, correlation IDs и outbox для событий.
7. Добавить структурные логи, метрики, трассировку и алерты.
8. Шифровать данные в канале и at rest, минимизировать PII и ввести retention policy.
9. Подписывать и версионировать ответы внешних источников.
10. Проводить SAST/DAST, dependency scanning, threat modeling и регулярный аудит прав.

## Модель угроз для основного сценария

| Угроза | Защита MVP | Production-усиление |
|---|---|---|
| Доступ к чужой заявке | проверка `company_id` и роль | policy decision point + audit alert |
| Подмена решения | state machine и policy version | подпись решения, four-eyes approval |
| Повторное применение действия | транзакционный журнал | idempotency key и outbox |
| Утечка реальных данных | используются синтетические данные | DLP, masking, vault, retention |
| Недоступность внешнего источника | локальный mock/fallback | timeout, retry, circuit breaker |
| Непрозрачная LLM-рекомендация | LLM не принимает решение | allowlist tools, prompt audit, human approval |
